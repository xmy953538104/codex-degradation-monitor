# codex-degradation-monitor

一个用来核对 **「我请求的模型」和「服务端实际返回的模型」是否一致** 的 Windows 小工具。

如果你怀疑自己的 Codex 账号被"降智"（请求旗舰模型，却被静默换成更便宜的模型），
这个工具能给你**硬证据**，而不是靠感觉。

---

## 判断依据（唯一依据）

```
你在请求里写：        "model": "gpt-6-astra"
服务端在回复里声明：   "response": { "model": "gpt-6-astra" }
                     ↑ 这两个不一致，就是换模的铁证
```

工具自己发一个**最小请求**（提示词就一句 `Reply with exactly: OK`，推理档位调到最低），
然后读服务端在 `response.created` 事件里**自己声明**的模型。

**这就是全部原理。** 没有猜测、没有启发式、没有主观判断。

---

## 它不会做的事

| | |
|---|---|
| ❌ 不修改 Codex 的任何文件 | 只**读** `~/.codex/auth.json`，一个字节都不写 |
| ❌ 不做中间人 / 不解密你的流量 | 它是自己发自己的请求，不需要证书、不改 TLS |
| ❌ 不伪装成别的客户端 | User-Agent 用**你本机真实的版本号**拼出来 |
| ❌ 不刷新、不改写你的登录凭据 | 凭据过期了就提示你重新同步，绝不自作主张 |
| ❌ 不上传任何东西 | 唯一的网络流量就是探测请求本身 |
| ❌ 不记录 access token | 日志和报告里只有 request-id 和账号 ID（用于核对） |

## 下载即用（推荐）

1. 打开本仓库的 **Actions** 页面，点最新一次成功的 `build`。
2. 在页面底部 **Artifacts** 里下载 `codex-degradation-monitor-windows`。
3. 解压得到 `codex-degradation-monitor.exe`，双击运行。

> 打正式版本时也可以直接在 **Releases** 里下载。

**首次运行会弹「Windows 已保护你的电脑 / 未知发布者」** —— 这是因为 exe 没有商业代码签名证书
（一年要几百到上千元）。点「更多信息」→「仍要运行」即可。这不是病毒提示，是"没交保护费"提示。

### 前置条件

你**必须先用过 Codex 并登录**（本机要有 `~/.codex/auth.json`）。
这是唯一没法打包进去的东西 —— 因为它是你的账号。

## 使用步骤

1. 双击运行。
2. 点 **「同步登录凭据」** —— 它会把你 Codex 的登录**复制一份**到工具自己的目录，
   之后工具只用这份副本。**换号之后重新点一下这个按钮就行。**
3. 勾选要探测的模型（默认只勾第一个，勾得越少消耗越小）。
4. 点 **「开始检测」**。
5. 看结论：

| 结论 | 含义 |
|---|---|
| **健康** | 请求的模型 = 服务端声明的模型 |
| **降级中** | 发现换模，会明确指出 `A → B` |
| **无法判定** | 请求成功，但没读到服务端声明的模型（会建议再测一次） |
| **探测失败** | 网络或凭据问题，会说明原因 |

6. 需要留证就点 **「导出报告」**，会生成一份 Markdown。

---

## 关于消耗

每次探测是一个极小的请求：一句话提示词 + 最低推理档位，**读到模型声明就立刻关闭连接**。
勾 1 个模型消耗最小；勾 4 个就是 4 倍（但每个都很小）。

---

## 关于 `x-codex-turn-state`

社区流传"该响应头长度 292=健康 / 312=降级"。**本工具把它当参考信息记录，但不作为判据。**

原因：

- 该说法来自社区逆向，**没有受控复现实验**；提出者本人也承认它不是官方质量指标
- Codex 官方客户端源码里**完全不校验**这个值的长度或内容
- 实测中它会在短时间内来回跳动，很像噪声

**权威判据永远只有一条：服务端声明的模型是否等于你请求的模型。**

|---|---|
| 凭据副本 | `~/.codex_state_monitor/credentials.json` |

## 设计取舍

### 为什么用"独立凭据副本"而不是直接用 `auth.json`

OAuth 的 refresh token 是**轮换**的：谁先刷新，另一方的 token 就作废。
Codex 自己会按它的节奏刷新，我们无法知道它何时刷新，所以两个进程共用一份文件必然出现竞态，
**可能把 Codex 的登录搞坏**。

独立副本把这个竞态变成非事件：最坏情况只是副本过期，用户再点一次同步即可。

### 为什么不做中间人抓包

我们评估过抓包方案（自签证书 + 解密 Codex 流量）。它能读到真实工作请求，
但代价是**必然改变 TLS 指纹**（要替 Codex 去握手），而且需要在本机留一把能解密流量的私钥。

本工具的方案**不需要伪装**：它就是一个正常的 API 客户端在发正常请求。
你担心的"被识别、被标记"在这个方案下不存在。

---

## 已知限制

- 探测用的是**低推理档位 + 一句话提示词**。它证明的是"在这个条件下服务端没换模"；
  不能 100% 等价于"你做长任务时也不会被换"。
- 如果 OpenAI 改了事件格式，`response.created` 里不再带 `model`，工具会报"无法判定"而不是瞎猜。
- 只能读本机已经登录的账号。
